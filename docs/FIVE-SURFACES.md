# The five surfaces

Where each one stands, what it shares, and what is genuinely left.

Captures live in `docs/captures/`, one folder per surface, regenerated by
`node scripts/capture-surfaces.mjs` with the dev servers up.

## Status

| # | Surface | Ships as | Auth | Live behavior |
|---|---|---|---|---|
| 1 | Customer | `apps/customer` — Expo, one binary per brand | Supabase guest JWT / email or phone OTP | Reads the tenant portal and storefront under RLS, subscribes to order/menu/drop revisions, and sends trusted writes to the platform API |
| 2 | Kiosk / POS | `apps/kiosk` — Expo, iPad landscape | paired device JWT | Reads its tenant menu and places an idempotent order through the API; native card-reader authorization is still simulated |
| 3 | Pickup display | `apps/display` — Next.js on a TV | paired, read-only device JWT | Reads the PII-narrow board view and reconciles on revision signals; fixtures are allowed only in development or explicit demo mode |
| 4 | Prep station | `apps/operator`, Prep tab | staff login | Reads location-day prep batches and recipes, subscribes to batch changes, and writes batch progress under RLS |
| 5 | Crew | `apps/operator`, Crew tab | staff login | Reads location-day shifts and checklists, attributes completions to the signed-in staff member, and reconciles each minute |

`apps/hq` is the sixth thing in `apps/` and is not one of the five: it is the
brand owner's console and the host for the platform API, not a surface in a
shop.

Every surface retains an intentional review path. Customer, operator, kiosk,
display, and HQ can render sanitized fixtures when explicitly running in demo
or without infrastructure; configured live paths never fall back to another
tenant's fixture data after a failed read.

## What they share

Everything below the screens is one copy, which is the point:

- **`@platform/domain`** — money, tax, order totals, sizes, fulfillment, cart,
  menu options, loyalty rules, search, and display projections. It is
  framework-free, so `node:test` reaches it and every surface can import it.
- **`@platform/data`** — direct reads under RLS, Realtime subscriptions, and
  the narrow projections used by display, operator, prep, and crew.
- **`@platform/schema`** — migrations and their TypeScript mirrors, with drift
  tests that inspect the SQL.
- **`@platform/ui`** — validated tenant tokens, copy, media geometry, motion,
  and shared components. Runtime consumers resolve through `ThemeProvider`;
  screens do not carry a second compiled palette.
- **`@platform/api-client`** — one authenticated contract for customer,
  kiosk, operator, and the HQ route handlers.

One order state machine sits underneath all of it: `orders` holds current
state, `order_events` is append-only, and a BEFORE INSERT trigger is the only
thing that can move `orders.status`. Five surfaces can point at one row safely
because none of them writes status directly.

## What each surface does differently, and why

The design language is one language; what changes per surface is scale, density
and posture.

**Customer** — phone portrait, thumb-reachable. Money rides the primary action.

**Kiosk** — a *standing* guest, 2–3 feet away, with a queue behind them. Targets
start at 60pt, the bag is a permanent rail, and the task is linear with no tab
bar. An idle clock resets an abandoned bag at 90 seconds but never counts down
an untouched attract screen.

**Pickup display** — read at 15 feet, glanced at for under two seconds, running
unattended for fourteen hours. The ticket number dominates. Motion is reserved
for the curbside-arrival badge, the only urgent signal on an ambient board.

**Prep station** — a bench tablet read by someone with flour on their hands.
Two states: bake list and recipe. Scaled quantities keep the recipe figure
beside them, and the allergen banner is pinned and not dismissible. The service
date follows the selected location's IANA timezone, not the tablet clock.

**Crew** — the personal staff surface: it shows names and attributes work.
Un-ticking is allowed because a checklist people cannot correct is one they
stop trusting. Its roster and calendar day advance while the tablet stays open.

## The keystone: `devices`

Kiosk and display are screens nobody signs into. The `devices` table was added
in migration 0022; migration 0038 completed the issue/refresh/revoke lifecycle.
Pairing mints a narrowly scoped device JWT carrying no staff `role`, so a device
token cannot satisfy a staff policy. Revocation and token version are checked
on every authorized read or order placement.

| Role | May | May not |
|---|---|---|
| `display` | read one location's PII-narrow board | write anything |
| `kiosk` | read the storefront and place an order | read other orders or customers |
| `pos` | kiosk capabilities plus attended-register posture | refund or edit the menu |
| `prep` | read recipes and move its own batches | touch orders |

## What is genuinely left

1. **Native card-reader authorization.** The kiosk creates real orders when
   paired, but `apps/kiosk/src/lib/card-reader.ts` is the explicit simulated
   seam. Square's Reader SDK requires a dev client/store build and production
   credentials, not Expo Go.
2. **Hosted cutover.** The EAS projects and release channels exist, but the
   owner must provision the hosted Supabase/Vercel/Square environments, apply
   migrations, connect locations, and run the real-stack acceptance checklist.
3. **Owner-controlled production facts.** Tax jurisdictions and legal text
   need owner/counsel approval; campaign delivery needs a push/SMS provider.
4. **Kiosk photography pipeline.** Live rows already prefer HTTPS
   `menu_items.image_url` and safely fall back to the tenant monogram. The
   current seed has no remote menu image URLs, so captures intentionally show
   monograms rather than borrowed or hard-coded art.

The remaining product/accounting caveats are maintained in
`docs/PRODUCTION.md`; dated audit documents preserve the state they measured
and are not rewritten as current documentation.

## What the backend is known to do

The integration suites run against real Postgres in CI and are designed to be
re-runnable:

```bash
export SUPABASE_TEST_URL=http://127.0.0.1:54321
export SUPABASE_TEST_ANON_KEY=...        # supabase status
export SUPABASE_TEST_SERVICE_ROLE_KEY=...
export SUPABASE_TEST_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
pnpm --filter @platform/integration-tests test
```

`five-surface-trace.test.ts` places one order through the real API route and
follows it through each surface's actual query: kiosk channel attribution,
database ticket assignment, the display-safe projection, operator transitions,
curbside arrival, prep completion, collection, and the crew day. Other suites
cover state transitions, idempotency, webhook replay and double-charge guards,
brand isolation, device scope, account deletion, and the claims hook.

## Regenerating the captures

Run these in separate terminals:

```bash
pnpm --filter @platform/customer exec expo start --web --port 4170
pnpm --filter @platform/kiosk exec expo start --web --port 4180
pnpm --filter @platform/operator exec expo start --web --port 4190
pnpm --filter @platform/display exec next dev --port 3200
node scripts/capture-surfaces.mjs
```

A surface whose server is down is skipped loudly; a live server that returns a
broken or missing page fails the run.
